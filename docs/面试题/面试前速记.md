# Agent 面试前速记

适用日期：2026 年 11 月 9 日。目标岗位为 Agent 应用研发，当前约有 3 小时准备。原图共 31 题；完整题目、口述答案、追问和资料链接见 [面试题整理与解答](./面试题整理与解答.md)。

今天的目标是能把一个系统讲完整：**为什么这样设计，怎么发现失败，如何验证改进有效。** 先练每题的第一段，追问时再展开；不要只背名词。

## 八段优先练熟的口述答案

### 介绍 Agent 架构

我会把系统分为入口、编排、模型、工具、知识、状态和评测几层。请求进入后先明确目标与约束，编排层按状态组装上下文，模型决定回答还是调用工具；工具层校验参数、权限和执行预算，结果写回状态，再进入下一轮。复杂任务增加计划、检查点和人工介入。最终是否完成由业务验收条件判断，生产上再用 Trace、成功率、时延和成本持续验证。

前端经验可以对应到：组件状态与任务状态、API Client 与模型适配、路由状态机与 Agent Loop、埋点与 Trace；另外要补上非确定性、工具副作用和结果评测。

### 解释 ReAct 和 Plan-and-Execute

ReAct 是根据当前观察决定下一步，行动后再观察，适合需要不断探索的任务。[ReAct 原论文](https://arxiv.org/abs/2210.03629) Plan-and-Execute 会先拆解任务、记录依赖，再执行和必要时重规划，适合目标清楚、步骤较多的任务。两者可以组合：外层维护计划，内层用 ReAct 完成子任务。生产系统还要用步数、时间、费用预算和独立完成检查来保证终止。

### 解释如何处理 Agent 死循环

我会先看 Trace，区分暂时性工具失败、状态没更新、观察信息不足和计划反复。对同一状态下的工具名及标准化参数做重复检测，记录已尝试路径和失败原因；连续没有新证据或任务进展时，就切换方法、重规划或请求用户补充信息。超时和最大步数负责兜底；权限不足、参数错误不能靠盲目重试解决，有副作用的操作还要保证幂等。

### 解释上下文压缩

先删重复日志、按需读取文件和工具，再对较早历史做结构化压缩。必须保留目标、硬约束、用户纠正、关键决策、证据位置、已完成事项和下一步。重要要求放在外部任务状态中，每轮重新注入。验证时看长任务成功率、约束遵守率和累计成本。压缩改变了历史前缀，可能影响缓存，因此要让稳定规则尽量保持不变，并把压缩调用本身也算进成本。

### 介绍 RAG 链路和优化

离线先做解析、清洗、切块、元数据与权限处理，再建立稀疏和向量索引。在线对问题做必要的改写，用 BM25 和向量检索互补召回，融合、去重，再用 Rerank 精排，最后把证据交给模型生成带引用的答案。排查时先确认正确材料是否入库、是否进入候选，再看排序、上下文拼装和生成，不能把所有问题都归因于模型。

### 解释评测怎么做

先定义业务成功标准和不能违反的约束，再构建有代表性的固定测试集。检索看 Recall@K、排序看 nDCG 或 MRR，生成看正确性和证据支持，Agent 看任务最终状态、工具副作用、成本和时延。确定条件用程序判分，开放式回答用校准过的模型评分加人工抽检。迭代先跑受影响的回归集，重要版本跑完整集，再灰度验证线上效果。

### 回答线上准确率突然下降

我会先确认“准确率”的定义和统计变化，划分时间、租户、问题类型与版本，必要时回滚。然后沿解析入库、召回、精排、上下文、生成逐层找第一个异常点，检查索引新鲜度、Embedding 版本、权限过滤、Prompt 和模型变更。用同一批失败请求对比新旧版本，单变量验证根因，修复后把案例加入回归集并灰度观察。

### 回答模型并发达到上限

先分清是并发数、每分钟请求数还是每分钟 Token 限制。入口使用有界队列、全局限流、按租户公平调度和超时取消，限制一个 Agent 的内部扇出。减少不必要轮次、输出长度和重复请求；对可重试的 429 或瞬时错误做有上限的退避。持续容量不足时申请配额或使用经过评测的备用模型。增加应用服务器不等于增加模型供应商配额。

## 必背公式

~~~text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2PR / (P + R)

Precision@K = Top K 中相关项数 / K
Recall@K    = Top K 中相关项数 / 全部已标注相关项数

RRF(d) = Σ_i 1 / (c + rank_i(d))
~~~

RRF 的 rank 从 1 开始，某一路没召回该文档就不加分；c 常从 60 起调。不要把 c 和返回数量 K 混淆。[Elastic RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

~~~text
BM25(q,d) =
Σ_t IDF(t) × f(t,d)(k1+1)
              / [f(t,d) + k1(1-b+b×|d|/avgdl)]

平均在途请求数 ≈ 请求到达率 × 平均处理时长
~~~

BM25 要能解释三个词：**稀有词更有区分度、重复出现收益递减、长文档需要归一化**。最后一个是稳定系统的平均容量关系，不能直接作为峰值容量承诺。

## 六个容易被追问的点

1. **Claude Code 并没有统一的官方“三层记忆”叫法。** 官方区分显式指令文件与 auto memory；再结合运行中的上下文可以作功能划分。如果对方问的是文件层级，就回答用户级、项目级、局部规则，并补充组织策略和本地文件。[Claude Code 记忆文档](https://code.claude.com/docs/en/memory)
2. **DeepSeek Harness 是具体开源工程。** 答“一切皆插件”，再讲模型适配、工具执行、Agent Loop 和会话事件如何协作，不要把 DeepSeek 模型的推理能力当成 Harness 设计。[官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)
3. **缓存命中仍占模型上下文。** Prefix Cache 复用计算；上下文压缩减少实际输入，两者解决的问题不同。[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
4. **检索 Precision 和回答正确率是两件事。** “知识找对了但答案错了”与“根本没找对知识”需要不同修复。
5. **Rerank 不能找回候选集合之外的材料。** 它主要解决排序，先保证候选覆盖。
6. **工具执行成功不等于业务完成。** HTTP 200、SQL 能运行、Agent 给出回答都不能单独证明任务成功。

## 前端转 Agent 的项目介绍

下面是可按真实经历改写的表达框架：

> 我的优势是把复杂流程做成可观察、可取消、可恢复的用户体验，并把前后端边界设计清楚。介绍项目时，我会先说明业务目标，再说明我亲手完成的模块，以及如何验证。Agent 方面重点讲状态编排、工具调用、证据检索和评测，最后讲一个实际问题的定位过程。

本仓库目前的 README 将项目定位为学习与实战教程，已完成工程基线、Vue/Fastify 链路和第 1 章，RAG、Memory、Workflow、Evaluation 仍在路线图中。若介绍这个仓库，应明确哪些已实现、哪些是设计方案；详解里的示例不能当作自己的生产经历。

被问到没有做过的生产场景时，可以直接说：

> 这部分我没有生产实测数据。我理解的关键风险是……如果负责落地，我会先建立……基线，用……指标比较方案，再通过……方式上线。

被追问优化数字时，用“测试集、基线、改动、前后值、成本副作用”的顺序回答。没有实测就说明实验设计；不要临时编一个百分比。

## 闭卷自测

1. 不看资料，画出完整 Agent 与 RAG 链路，并说出状态存在哪里。
2. 举例解释为什么上下文更短了，某一轮账单反而可能更高。
3. Top 10 里有 4 个相关片段，标注集总共 8 个相关片段，算出 Precision@10 和 Recall@10。
4. 正确 chunk 已在 Top 50，但没进入最终 Top 5，下一步检查什么。
5. 用户说“SQL 查出来不对”，为什么不能只看 SQL 是否执行成功。
6. 说出一个重复调用可以接受、另一个必须阻止的例子。
7. 用 90 秒讲清一个真实案例：现象、证据、根因、修复、验证。

第 3 题答案：40% 和 50%。其余题按“结论 → 机制 → 场景 → 验证 → 取舍”组织，通常比堆术语更清楚。
