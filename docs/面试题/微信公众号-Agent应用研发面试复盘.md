# Agent 面试复盘｜从多轮会话到 RAG 和线上排障

A 问订单助手「上个月已支付订单为什么少了？只做分析，按北京时间统计。」聊了几轮后，他补了一句「按渠道拆开看」。同一时间，另一个公司的 B 也在查订单。

两人共用一套 Node 服务和模型接口。A 的追问里没写月份、订单状态或公司名称，后端怎么接上前面的对话，又怎么保证两个人都只查到自己有权访问的数据？

## 01 两个人同时聊，后端怎么分开会话？

租户通常对应一个公司或组织。同一个租户里可以有很多用户，一个用户也可以打开多段对话。后端先验证登录身份和租户成员关系，再检查用户能否访问请求中的 `conversationId`。这个 ID 负责定位会话，访问权由后端判断。

**模型客户端可以复用，会话消息按归属读取。** 用 Node 写接口时，每次请求都可以创建新的执行对象，再从数据库加载对应会话。把消息和任务进度放在持久层，服务重启之后，A 还可以继续聊。

以接收 `messages` 的接口为例，后端给 A 的追问补上本轮需要的历史。B 的请求走同一套代码，但用自己的身份和会话加载数据。即便模型服务提供会话续接 ID，应用仍要保存它与自己会话的对应关系，使用前做同样的访问检查。

这几个 ID 在面试里值得分清。`tenantId` 和 `userId` 用来确定访问范围，`conversationId` 标识多轮对话，`runId` 标识一次任务执行。一次运行里可以有多次模型调用。A 在同一个会话里连续提交两次时，可以让请求串行处理，或者在写入时检查状态版本。

隔离也要延伸到工具、检索和缓存。查知识库时用后端确认的租户和文档权限作为检索条件，命中缓存时也要校验它对应的数据范围与版本。

## 02 从一句追问到一次可控的工具调用

接到 A 的追问后，编排层加载任务状态和统计口径，模型适配层负责发请求并收集用量，模型根据当前信息提出下一步动作。比如，它可以要求按渠道查询订单。工具执行层校验参数、身份和查询范围，再执行只读查询。结果写回任务状态，下一轮模型据此解释下滑来自哪些渠道。

这套负责调用、执行和恢复的运行系统通常叫 **Harness**。除了模型和工具，它还要管理上下文、预算、检查点和停止条件，并留下能回放的 Trace。DeepSeek Harness 给出了一个插件化实现。它用 Cordis 组织服务和事件，模型适配、工具注册、会话日志和 Agent 循环都可以通过配置替换。[DeepSeek Harness 架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

**ReAct 适合根据观察调整下一步。** 比如查询发现某个渠道的订单量骤降，Agent 可以再查该渠道的分周数据。Plan-and-Execute 会先列出可跟踪的步骤和依赖。订单分析可以用外层计划维护「确认口径、查总体变化、拆渠道、核对结论」，某一步里面再用 ReAct 补查证据。[ReAct 论文](https://arxiv.org/abs/2210.03629)

遇到反复调用，先看第一次重复时的状态。相同工具、参数和状态版本连续出现，且没有得到新证据，往往说明要换方法。参数错误可以把缺失字段告诉模型，权限不足就结束该动作，短暂网络错误才做有限重试。

运行器要设置步数、时长和费用上限。任务结束前，用可检查的条件验收结果，比如渠道数据是否齐全，报告里的结论能否从数据推出来。

写操作需要单独处理。比如保存报告时响应超时，报告可能已经写入。检查点保存的是任务进度，恢复时用同一个幂等键核对之前的写入结果，再决定是否重试。

## 03 聊得越来越长，哪些内容还要发给模型？

一段对话的完整历史可以存在数据库里。组装模型请求时，从里面选当前需要的内容。先给输出和下一次工具返回留空间，再考虑放进多少近期消息、旧历史摘要和证据。

A 在第一轮确认了「只读」「已支付」「北京时间自然月」。这三个要求应该保存在可更新的任务状态里，每轮重新加入有效要求，关键权限再由工具执行层校验。摘要可以保留目标、已确认事实、决策依据、失败原因、证据 ID 和待办。大结果留在外部，按需读取，工具调用与对应结果要成对保留。

工具也占上下文。Skill 可以先提供名称和用途，需要时再读操作说明。通过 MCP 接入大量工具时，可以先按权限过滤目录，再加载当前任务需要的工具说明和参数 Schema。工具返回几千行数据时，在服务端聚合或分页，再交给模型处理。[Anthropic 上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**压缩能省多少，先看算的是哪笔账。** 假设一次输入有 8,000 Token 的固定规则、40,000 Token 的旧历史和 8,000 Token 的近期消息。把旧历史压到 6,000 Token，单次输入就从 56,000 降到 22,000，约少 60.7%。

这组数字只衡量输入长度。命中缓存的 Token 仍占上下文，改写历史也可能使原来的前缀失效。对按前缀复用的服务，可以把稳定规则放在前面，动态摘要放在后面。算费用时要把压缩调用、缓存读写和之后每一轮都纳入。[Claude 提示词缓存说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

验证效果时，让同一批长任务从相同检查点继续跑，对照压缩前后的约束遗漏、任务完成率、重复步骤和累计成本。

面试里如果问到 Claude Code 的「三层记忆」，先确认对方说的是作用域还是用途。按用途可以讲当前工作上下文、项目规则和自动记忆。官方文档把 `CLAUDE.md` 等规则文件和 auto memory 列为跨会话携带信息的两种机制。[Claude Code 记忆文档](https://code.claude.com/docs/en/memory)

## 04 RAG 找指标口径，查询工具取订单数据

A 要查的是订单变化。检索增强生成（RAG）先找「已支付订单」的指标定义、数据字典和适用规则，再把相关证据交给模型。统计口径确定后，查询工具从业务库取实际订单数。

### 入库时保留结构、版本和权限

技术文档可以先按标题、段落和表格结构切分，再用 Token 上限控制长度。固定长度适合做基线，递归切分尽量保留自然边界，语义切分按主题变化取边界。需要兼顾命中精度与上下文时，可以检索小块，命中后补上父章节。表格分块时要带上列名和单位。

每个片段应能追溯到文档、版本和原文位置，并保留租户、权限及向量模型版本。文档更新时，可以在模型和预处理相同的前提下，用内容哈希识别可复用的向量。先写入并校验新版本，再切换当前有效版本。

重切后多余的旧块、被删除的文档和过期的缓存也要处理。选向量库时，可以用实际读写负载比较权限过滤后的召回、查询延迟、更新生效时间和运维成本。

### 召回、融合、精排各看一件事

BM25 擅长找术语、字段名和编号。它综合词频、词在语料中的稀有程度和文档长度，词频增加带来的收益会逐渐饱和。向量召回补充语义相近的表达。多轮查询还可以先把「按渠道拆一下」补成带时间范围和指标名称的检索问题。

两路结果可以用 RRF 按名次融合。片段在某一路排第 `r`，就贡献 `1 / (c + r)`，对召回它的各路求和。Elasticsearch 的平滑常数 `c` 默认是 60。每路候选数量和最后交给模型的 Top K 需要分别选择。[Elasticsearch RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

候选齐了之后，可以用 Reranker 精排。常见的 Cross-Encoder 会把问题和每个候选片段一起送进模型打分，优先留下满足条件的材料。若正确片段根本没进候选，先查文档是否入库、是否被切散、权限和版本条件是否正确，再调召回规模或查询方式。

评测时，假设 Top 10 里有 4 条相关证据，标注集一共有 8 条相关证据，那么 **Precision@10 是 40%，Recall@10 是 50%**。还要另看回答是否用了这些证据、引用是否支持结论。

### 行业黑话最终要落到表和字段

做 Text2SQL 时，行业简称和近义词只能帮忙找到候选。术语词典还要把业务定义连到具体表、字段、关联关系和枚举值。比如「实付订单」要核对支付状态、去重口径和时间字段。如果退款是否计入会影响结果，就按已确认的指标定义执行，或先澄清。

SQL 由受限的只读工具执行。运行前校验允许访问的表、操作类型和查询范围，评测时用已知数据核对统计值，判断查得出的数字是否符合用户问的口径。

## 05 评测要核对什么，才能说这次改动有效？

给订单助手准备一组有已知结果的任务。比如固定两个月的样例数据，要求 A 的查询只统计支付成功的订单，按北京时间分月，并返回每个渠道的变化。用程序核对查询结果、时间边界和权限。对「解释是否清楚」「引用是否支持结论」这类开放判断，再用带评分标准的模型评审和人工抽查。

数据集既要覆盖常见查询，也要覆盖多轮纠正、无证据、旧版本冲突、工具超时和跨租户访问。可以从脱敏的真实任务抽样，再补充能验证的难例。按文档、时间或用户拆分调优集和测试集，避免近重复问题让分数看起来偏高。

每次评测记录数据快照、模型、Prompt、工具、索引和评分器版本，并保留任务结果、耗时与用量。同一批任务做前后对照，容易波动的用例多跑几次。确定的业务约束可以直接做断言，模型走哪条可行路径则留给它选择。[Anthropic Agent 评测指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

平时改一个工具，可以先跑相关回归和过去的失败样本。改全局 Prompt、模型或索引时，再跑完整集。离线通过后用小流量灰度观察。如果线下分数不错但用户仍觉得难用，就回看真实会话里是否有更多指代、省略、权限差异或超时。首字出现快和任务完成快也要分别记录。

## 06 线上答错了，从哪里开始查？

收到准确率下降的告警，先确认变化发生在证据召回、答案正确率，还是任务完成率。按时间、租户和发布版本划分样本，再挑一条失败请求定位。

**一个假设案例。** 指标文档已把统计时间改成支付时间 `paid_at`，助手却继续引用旧口径，用创建时间 `created_at` 汇总。用户看到引用链接能打开，结果依然和报表不一致。

按 `runId` 找到那次运行，沿入库、召回、精排、上下文和生成逐段看。如果新版本已经入库，召回结果却混入旧片段，且旧片段最终进入模型请求，就可以用同一问题做对照。保留模型和 Prompt，只让当前有效版本参与检索，看查询口径是否恢复。

如果实验支持这个判断，修复索引发布和缓存失效逻辑，把文档缩短、删除、乱序更新也加入回归。灰度后观察旧版本命中、更新生效时间、答案正确性和 P95 查询延迟。

为了做这样的排查，Trace 至少要串起会话和运行 ID、排队与耗时、模型和 Prompt 版本、检索前后候选、实际引用的文档版本、工具参数和结果引用、状态变化以及最终验收。敏感内容用受控引用和脱敏字段记录，调用用量和错误码留给排障和成本分析。

### 请求太多，先确认打满了哪种配额

并发是同时在途的调用数，RPM 是每分钟请求数，TPM 是每分钟 Token 数。假设平均每秒进入 2 个任务，每个任务调用模型 4 次，每次占用 3 秒，稳态下平均约有 24 次模型调用在途。还要用真实流量验证突发和长尾。

在模型入口做全局限流、有界队列和租户配额，限制单个任务的并行调用数。队列要有等待期限，用户取消后及时释放资源。遇到可重试的限流或瞬时故障，可以有限退避，计入任务预算。持续容量不足时，再评估减少调用轮次、路由到已验证的备用模型或申请更多配额。

线上可以同时看业务完成率、首 Token 和任务完成时间、工具错误、429、排队时间和每个成功任务的成本。按租户、任务类型和版本分开看，才能发现总体指标掩盖的局部退化。

## 面试时，把一条请求讲完整

如果面试官让你介绍 Agent 项目，可以用一个任务说明你的职责、设计和验证过程。比如从 A 的「按渠道拆开看」开始，解释应用怎么找到这段会话、加载上一次确认的口径、检索当前有效文档、用只读工具查数据，再说明如何验证结果。

被追问「遇到过什么问题」时，选一个自己处理过的故障，讲清预期与实际差在哪里、哪条记录支持你的判断、改完怎样复现验证。项目还在实验阶段，也可以直接讲跑过的本地用例和它能证明的结果。
