# Agent 应用研发面试 31 问

一个订单分析 Agent 既要接住用户的追问，也要找对统计口径、按权限调用工具，最后交出能核对的结果。面试里，架构题往往会顺着这条链路继续问到上下文、RAG、评测和线上故障。

## 一、整体架构

### 1.1 Agent 项目的整体架构是什么？

入口负责认证、会话和请求校验。A 和 B 同时使用同一个 Node 服务时，后端按各自的租户、用户和会话 ID 读取历史，检查他们能访问哪些数据。

编排层加载任务状态和相关证据，通过模型适配层发出请求。模型提出动作后，工具层校验参数和权限，执行并把结果写回状态，供下一轮决策。知识库提供可引用的资料，持久层保存消息、进度和检查点。

任务结束时用业务条件验收。比如订单分析要核对时间、指标口径和查询结果。Trace 用来串联这次运行，评测再检查任务成功率、时延和成本。

### 1.2 Claude Code 的三层记忆架构是什么？

面试里可以按用途理解成三类。**当前工作上下文**放本次任务的对话、文件和工具结果。**持久规则**由用户或团队通过 `CLAUDE.md` 等文件提供。**自动记忆**积累可供后续会话使用的经验和偏好。

这个划分把当前工作也算在内。Claude Code 文档把规则文件和 auto memory 列为跨会话携带信息的两种机制。如果对方问的是文件作用域，可以分别讲用户级、项目级和按路径生效的规则。[Claude Code 记忆文档](https://code.claude.com/docs/en/memory)

### 1.3 了解 DeepSeek Harness 吗，说说它整体的设计？

DeepSeek Harness 采用插件化架构，底层用 Cordis 组织服务、事件与插件生命周期。模型适配、工具注册、会话日志和 Agent Loop 都可以通过配置组合或替换。不同运行形态由 profile 和 bundle 组合。

执行时，循环领取用户输入，组装上下文与工具定义，再发起模型请求。工具调用和结果进入会话事件日志，供后续构建上下文、续接会话和排查问题。这样的扩展方式需要同时管理插件依赖、事件顺序和配置版本。[DeepSeek Harness 架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

### 1.4 一个完整的 Harness 至少包含哪些部分？

- **模型适配和执行循环**统一请求与响应，推进模型调用、工具执行、完成和取消。
- **上下文和状态**管理任务目标、约束、历史、证据和检查点。
- **工具执行边界**负责注册、参数校验、授权、超时、幂等与资源预算。
- **恢复和验收**按错误类型决定是否重试，记录 Trace，并检查实际业务结果。

例如保存报告后连接断开，恢复时要用同一个操作 ID 查询写入是否已经成功。检查点告诉程序走到了哪一步，业务库的幂等约束负责防止重复创建。

## 二、ReAct 与执行循环

### 2.1 Agent 中 Plan-and-Execute 模式和 ReAct 模式有什么区别？

**ReAct 根据眼前的观察选择下一步。** 查询发现某个渠道的订单骤降，就继续查看该渠道的分周数据。反馈快，适合搜索、调试这类需要探索的任务。[ReAct 论文](https://arxiv.org/abs/2210.03629)

**Plan-and-Execute 先维护一份显式计划。** 它记录子任务和依赖，执行中根据结果更新计划，适合步骤较多、目标可拆解的任务。

两种模式可以组合。订单分析的外层计划安排口径确认、总体查询、分渠道和结果核对，分渠道这一步再通过几轮 ReAct 补充证据。比较效率时要把规划、重规划和执行的总成本算在一起。

### 2.2 怎么解决 ReAct 模式中死循环和路径重复的问题？

给动作记录工具名、规范化参数和相关状态版本，结合最近几步的轨迹识别重复。即使工具名交替变化，只要状态没推进、也没有新证据，就可以触发换方法、重规划或请求用户补充信息。后台轮询则按间隔、期限和任务状态单独判断。

参数错误应反馈具体字段，权限失败应结束该动作，临时网络错误可有限重试。运行器给步数、耗时和费用设上限。到达上限时，返回已经完成的部分与阻塞原因。

### 2.3 Agent 执行任务时路径反复、重复尝试，可能原因是什么？如何优化？

从 Trace 找第一次重复，回看当时的状态和工具反馈。

- **已完成的步骤又做了一遍。** 检查状态是否写回，恢复时是否读到了完成记录。
- **一直提交错误参数。** 明确 Schema，用字段级错误说明反馈给模型。
- **换了查询词，结果还是同一批。** 检查证据缺口，拆出子问题或换资料来源。
- **方案改了几轮，结果仍无法验收。** 把目标拆成可检查的里程碑，必要时向用户澄清。

用同一批失败任务复放，比较重复调用比例、任务完成率和耗时。比如「已完成子任务被再次执行」这个用例，就要检查恢复后的实际行动。

## 三、上下文工程

### 3.1 Agent 上下文越来越长，有什么应对方式？

先给本轮输出和后续工具结果预留空间，再选要发送的内容。保留当前目标、有效约束和近期交互，把较早的历史压成结构化摘要。原始历史、文件和证据放在外部存储，需要时按 ID 查回。

工具只返回本轮需要的字段或聚合结果。任务可拆时，让每个子任务只读自己需要的资料，返回结论、证据和待解决的问题。[Anthropic 上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 3.2 上下文压缩时一般保留哪些关键信息？如何判断哪些内容可以被丢弃？

判断标准是后续步骤是否要用到这条信息，以及能否准确找回。保留目标、用户确认的硬约束、事实、关键决定和依据，还要记下完成项、待办、失败原因、证据 ID 与未结束的调用。

重复日志、已经失效的探索记录可以移出活动上下文。大文件和原始结果留在外部，摘要中保留位置与版本。若模型接口需要保留工具交互记录，调用和结果应按协议成对处理。

### 3.3 如何避免 Context 压缩之后，模型忘记用户之前提出的重要要求？

把有效要求存成独立清单，为每项保存 ID、原意、来源和状态。用户修正口径时，更新相应条目。每轮从清单重建上下文，压缩和恢复后检查仍有效的要求是否都已带上。

例如用户在第一轮要求「只读，按北京时间自然月统计」，应用每轮带上这两条。工具用只读数据库权限约束操作，程序再检查实际查询的时间边界。评测里专门放入很早提出、很晚才会生效的要求。

### 3.4 真实系统中，Context 压缩过后对 Prefix Cache 的影响有多大？Token 消耗量具体减少了多少？

压缩后的摘要会改变请求前缀。对按前缀匹配的缓存，改变位置之前稳定的规则仍可能复用，改变之后要按供应商的缓存边界重新判断。命中缓存的 Token 仍占上下文窗口。

假设固定规则 8,000 Token、旧历史 40,000、近期消息 8,000。把旧历史压到 6,000，输入就从 56,000 降到 22,000，单次输入长度约少 **60.7%**。

这是演算。测实际成本时，分别记录未缓存输入、缓存读取、缓存写入和输出，并把摘要调用及后续各轮一起算进去。如果旧历史本来大量命中缓存，压缩后的第一轮可能更贵。[Claude 提示词缓存说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

### 3.5 Context 压缩后的效果是如何检测的？

让同一批长任务从同一检查点分成两组，一组保留完整历史，一组用压缩后的上下文。固定模型、工具和数据版本，再比较后续执行。

要核对关键事实和约束有没有保住、任务是否做完、已完成步骤有没有被重复，还要看总时延和费用。用例可加入用户多次纠正、长工具输出、连续压缩和中断恢复。容易波动的任务多跑几次，再看各组的差异。

### 3.6 如果 Skill 或 MCP 非常多，全部放进上下文中占用了太多部分，有什么办法解决？

先提供精简目录，按用户权限和当前任务筛选，再加载用得上的说明。Skill 可以先给名称与用途，命中后再读正文和相关资源。通过 MCP 接入的工具，可以先检索简短描述，再加载完整参数 Schema。

执行结果也要控制体积。查询返回几千行时，可以聚合、分页，或者给出摘要和可查回的结果 ID。用工具选择正确率和任务成功率检查按需加载是否漏掉了必要能力。

## 四、RAG 与知识库

### 4.1 BM25 召回的原理是什么？

BM25 给词项匹配打分。一个查询词在文档中出现得越多，分数通常越高，但增加会逐渐饱和。它在整个语料里越少见，区分度越高。文档长度也会归一化，减少长文档因词多而获得的优势。

每个词的分数可以写成 `IDF × tf × (k1 + 1) / (tf + k1 × L)`，再把查询词的分数相加。这里的 `tf` 是词频，`L = 1 - b + b × 文档长度 / 平均文档长度`。参数 `k1` 控制词频饱和，`b` 控制长度归一化。

倒排索引可以先找出包含查询词的候选。BM25 适合匹配接口名、错误码和行业术语，向量召回可以补上语义相近的表达。[Lucene BM25Similarity 文档](https://lucene.apache.org/core/9_9_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)

### 4.2 准确率和召回率是什么？分别怎么检测？

「准确率」要先确认统计对象。分类任务的 Accuracy 是预测正确的样本数除以全部样本数。在检索里，**Precision 看返回结果中有多少相关项**，**Recall 看应找到的相关项中找到了多少**。

给问题标注相关证据，固定评价单位和返回条数。假设 Top 10 有 4 条相关，标注集一共 8 条相关，那么 `Precision@10 = 4 / 10 = 40%`，`Recall@10 = 4 / 8 = 50%`。

最终答案另行检查事实、引用和结论。对无可用证据的问题，可以评价是否合理澄清或拒答。

### 4.3 在 Text2SQL 场景中，针对行业黑话和专业术语，怎么解决召回不准的问题？

先把业务词映射到指标定义，再把定义关联到表、字段、连接关系和枚举值。术语库要保存别名、计算口径和适用版本。检索时结合关键词和向量召回，同时查找经过验证的 SQL 示例。

假设「动销商品」指某周期内至少有一笔符合条件成交的商品。模型需要知道哪种状态算成交、用哪个时间字段，以及按哪个商品 ID 去重。退款是否计入有歧义时，先核对业务定义或澄清。

生成的 SQL 交给只读工具，按租户范围、表权限和资源上限执行。评测用固定数据核对查询结果。

### 4.4 想要提升 RAG 的召回率，通常有哪些手段？

先找正确证据在哪一步丢了。文档没有入库就补数据，表头或正文解析有误就修解析，答案被切断就改切块和相邻片段扩展。

在查询端可以补全指代、展开行业别名、把复杂问题拆成子问题。检索端用 BM25 与向量互补，检查查询和文档的向量模型是否匹配，再调近似近邻索引的搜索参数和候选规模。

用同一批标注问题对比 Recall@K、最终答案和 P95 延迟。扩大候选池后，再看增加的证据是否抵得过噪声与计算开销。

### 4.5 RAG 离线阶段的 chunk 切分方式一般有哪些，分别有什么优势？

- **固定长度**易实现，也容易控制每块的大小，适合作为基线。
- **递归切分**优先按段落、句子等边界拆分，尽量保持表达完整。
- **按文档结构切**保留标题、表头或代码块，便于理解和引用。
- **语义切分**根据主题变化寻找边界，适合结构标记少的长文本。
- **父子切分**用小块命中具体知识，必要时补上父段落或章节。

可以先按文档结构切，再加长度上限。表格分块要保留列名和单位。块大小、重叠与扩展范围用实际问题验证，同时看证据覆盖、答案完整度和索引成本。

### 4.6 如果我的文档需要频繁更新，向量库应该怎么设计和选型？

保留稳定的文档 ID、版本、片段 ID、内容哈希、权限和 Embedding 版本。文档变更后增量处理，重复事件按幂等规则写入，旧事件按版本号判断。向量模型和预处理一致时，未变化的片段可以复用向量。

新版本先写入并校验完整性，再发布为有效版本。查询按当前版本和权限过滤。文档缩短、删除或撤销权限时，旧片段和相关缓存也要同步处理。大规模换向量模型时，可构建新索引验证后再切换。

选型从现有条件出发。已有 PostgreSQL 且需要和业务表关联，可以评估 pgvector。向量服务独立时，可以评估 Qdrant。需要在同一系统中做全文和向量检索时，可以评估 Elasticsearch。

用实际读写流量测权限过滤后的召回、P95 时延、更新生效时间和运维成本。[pgvector 说明](https://github.com/pgvector/pgvector) · [Qdrant 向量数据管理](https://qdrant.tech/documentation/manage-data/points/)

### 4.7 Rerank 的原理是什么，为什么能够优化 chunk 的排序？

向量召回通常分别编码问题和片段，按向量相似度快速取候选。常见的 Cross-Encoder 精排会把问题与每个候选片段一起输入模型，重新计算相关性。这样可以更细致地判断实体、否定和多重条件是否匹配。

联合打分需要为每个候选做计算，因此通常用在小候选集。它能调整候选顺序。正确证据能否进入候选，要先看召回。评测可固定候选集，比较排序指标、进入上下文的证据和新增延迟。[Sentence Transformers 检索与精排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

### 4.8 RRF 算法的公式是什么，K 一般设置多大？

RRF 按名次融合多路检索结果。文档 `d` 的得分是 `RRF(d) = Σ 1 / (c + rankᵢ(d))`。`rankᵢ(d)` 是它在第 `i` 路的名次，从 1 开始。只对召回该文档的路求和。

如果题里的 `K` 指平滑常数，这里记为 `c`。Elasticsearch 默认值是 **60**，可作为调参起点。常数越大，各名次的贡献越接近。每路候选窗口和最终返回 Top K 分别按证据覆盖和延迟选择。

用 `c = 60` 演算，A 的两路名次是 1 和 10，得分约 0.03068。B 两路都排第 2，得分约 0.03226，所以 B 排在 A 前面。[Elasticsearch RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

## 五、评测体系

### 5.1 一个完整严谨的评测流程应该怎么设计？

先定义任务怎样才算完成。订单助手的标准可以是查对时间、状态和渠道维度，数字与固定数据集一致，并遵守只读限制。

准备代表性用例，固定模型、工具、数据和索引版本，跑出基线。分开检查证据召回、答案质量、工具行为和最终业务状态。可确定的结果用程序断言，开放式回答用带评分标准的模型评审，再用人工抽查校准。

在同一组任务上对比改动前后，波动大的任务重复运行。分析首个出错步骤，达到质量、时延和成本门槛后再灰度。新出现的失败加入回归集。[Anthropic Agent 评测指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### 5.2 一次评测中哪些东西需要记录？重点关注哪些指标？

记录应能解释前后差异，也能支持回放。保存样本 ID、输入、验收条件、数据快照、模型与采样参数，以及 Prompt、工具、索引和评分器版本。关联运行 ID、实际输入输出引用、工具结果和最终状态。

质量看任务成功率、证据覆盖、答案正确性与约束违反。性能看首 Token、完成时间、排队和步骤数。成本看输入、输出与缓存用量，以及每成功任务成本。

有成功任务时，可以用总费用除以成功数，分子也计入失败尝试的费用。这样可以看出反复重试带来的实际开销。

### 5.3 每次迭代都需要完整评测吗？想要更敏捷的评测流程，应该如何改造？

按改动风险分层运行评测。

1. **快速冒烟**覆盖基本调用、权限和停止条件。
2. **定向回归**覆盖受影响模块和历史失败样本。
3. **完整基准**在重要发布或更换模型、全局 Prompt、Embedding 时运行。
4. **线上灰度**用小流量验证真实依赖与用户体验。

给用例标上依赖的模块、数据和版本，就能快速选出该跑的集合。复用中间结果时，让缓存键包含相关版本。关键权限和副作用检查可以保持每次都跑。

### 5.4 离线评测效果 OK，但生产环境用户反馈体验不好，应该怎么处理？

先把「不好用」拆成可观察的现象，比如答案错、任务没做完、等待太久或不知道进度。抽取真实失败会话和 Trace，按租户、任务类型和版本看差异。

再比较线上与离线条件。线上可能有更多多轮省略、权限差异、旧索引命中和工具限流。也可能是评分偏爱完整长文，用户实际只需要明确结论。

把缺失场景补进评测集，修复后观察受控流量里的任务完成率、用户纠正和等待时间。首字时延和完整任务时延分别记录。

### 5.5 评测数据集应该怎么构造，重点关注哪些方面？

从脱敏的真实任务抽样，覆盖常见分布，再补充无答案、术语歧义、多轮纠正、工具故障、权限和跨租户隔离等长尾用例。

每条用例写清输入条件、期望证据或最终状态、允许的动作和必须遵守的约束。能用固定数据判断的结果，提前写好断言。

按文档、用户或时间切分调优集与测试集，避免相似样本反复出现。上线后持续收集真实失败，分类加入回归集。

## 六、线上运行与排障

### 6.1 现在线上的 RAG 系统准确率下降很多，你会怎样排查问题？

先确认变化的是证据召回、答案正确性，还是任务完成率。核对指标定义、样本量和发布记录，按时间、任务类型、租户和版本缩小范围。影响较大时，可以先回滚到可用版本。

挑一条失败请求，顺着**解析入库 → 召回 → 精排 → 上下文 → 生成**检查。看正确证据有没有入库、能否进入候选、有没有被排序或长度预算挤掉，以及最后是否用对。

用相同问题做单变量对照。比如固定模型和 Prompt，只替换索引版本。找到第一个变差的环节后修复，把原失败与相邻边界用例加入回归。

### 6.2 线上运行时的 Agent 系统，你会关注哪些指标？

- **任务结果**看完成率、人工接管、用户纠正与抽样正确性。
- **等待体验**看首 Token、P95 完成时延和排队时长。
- **运行稳定性**看超时、429、工具失败、重复调用、取消和恢复。
- **资源与知识**看在途请求、Token、每成功任务成本、索引新鲜度与旧版本命中。

按租户、模型版本和任务类型分开看。比如首 Token 变快但完成时间变长，就进一步拆出模型、工具和等待环节。

### 6.3 Agent 系统一次运行的 Trace 会记录哪些东西？

根节点记录 `traceId`、`runId`、会话、租户、任务类型、起止时间和最终状态。排队、模型、检索、工具与验收各自记录为子步骤，便于沿一次任务查问题。

模型步骤记录版本、输入输出引用、Token 和停止原因。检索步骤保存改写问题、过滤条件、候选名次、索引版本和最终证据。工具步骤记录调用 ID、脱敏参数、授权判定、结果引用、超时和重试。

再记录检查点、状态变化和验收条件。大结果通过受控引用查回，敏感字段按需脱敏。总时延从根节点读取，分析慢在哪里时看关键路径。成本按各次调用的用量汇总。[OpenTelemetry GenAI 观测说明](https://opentelemetry.io/blog/2026/genai-observability/)

### 6.4 线上出现 badcase，你会怎么分析？举一个你遇到的例子。

先明确预期和实际偏差，保留当时的 Trace、数据版本与权限条件，再复放同一请求。沿链路找第一次偏离的地方，用对照实验验证假设。

以一个**演练案例**来说，差旅政策更新后，助手仍给出旧住宿标准。回看 Trace，发现同一文档的新旧片段同时被召回，旧片段进了模型请求。固定模型和 Prompt，只让当前有效版本参与检索，再核对回答和引用。

如果对照恢复正常，就修复索引版本发布、旧片段清理和缓存失效。回归覆盖文档缩短、删除与乱序更新，灰度观察旧版本命中率和更新生效时间。面试里可以用自己处理过的案例讲清职责、证据、修复和验收。

### 6.5 Agent 系统请求非常多，达到了模型并发上限，应该怎么解决？

先区分同时在途的**并发数**、每分钟请求数 **RPM** 和每分钟 Token 数 **TPM**。假设每秒 2 个任务、每任务 4 次模型调用、单次占用 3 秒，稳态平均在途调用约为 `2 × 4 × 3 = 24`。

同一假设下约需 480 RPM。若每次调用按配额口径消耗 3,000 Token，则约需 144 万 TPM。实际还要考虑流量突发、时延分布和供应商的计量规则。

在共享模型入口做全局限流、有界队列和租户公平调度，控制任务内部并行调用数。给队列设等待期限，取消时释放资源。可重试错误按服务端提示做有限退避，重试也计入预算。[AWS 重试控制指南](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)

持续容量不足时，减少重复调用和无关上下文，评估已验证的备用模型或申请配额。上线前对比任务成功率、排队、429、尾延迟和每成功任务成本。
