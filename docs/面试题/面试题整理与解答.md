## 1 整体架构方面

### 1.1 Agent 项目的整体架构是什么？

**口述答案**

我会按职责分为交互入口、任务编排、模型适配、工具执行、知识检索、状态记忆和评测观测。请求进来后先明确目标和约束，编排层组装上下文，让模型选择下一步；工具层负责参数校验、权限和实际执行，结果写回任务状态，再进入下一轮。复杂任务增加计划、检查点和恢复机制。任务完成要依据业务验收条件，运行过程则用 Trace、成功率、时延和成本来验证。

**各层分别解决什么**

| 层 | 关键职责 | 典型内容 |
| --- | --- | --- |
| 交互与接入 | 身份、租户、输入校验、流式反馈、取消 | Web/API、任务 ID、SSE |
| 编排 | 目标拆解、循环、路由、停止、人工介入 | Workflow、ReAct、计划与执行 |
| 模型适配 | 统一请求和响应、模型路由、超时、用量 | Model Adapter、结构化输出 |
| 工具执行 | 注册、Schema 校验、权限、沙箱、幂等 | 数据库、搜索、文件、MCP |
| 知识检索 | 入库、索引、召回、精排、引用与权限 | RAG、业务词典、元数据 |
| 状态与记忆 | 运行状态、会话、检查点、长期知识 | Run State、Checkpoint、Memory |
| 评测与观测 | 记录过程、判断效果、定位回归 | Trace、离线评测、线上指标 |

~~~mermaid
flowchart TD
  A["用户与业务请求"] --> B["接入层：身份、租户、校验"]
  B --> C["编排层：目标、状态、预算、停止条件"]
  C --> D["上下文构建"]
  E["知识检索与持久状态"] --> D
  D --> F["模型决定下一步"]
  F --> G{"回答或行动"}
  G --> H["工具参数与权限检查"]
  H --> I["执行并记录结果"]
  I --> C
  G --> J["完成条件与结果检查"]
  J --> K["返回答案或待处理事项"]
  C -.-> L["Trace 与评测"]
  I -.-> L
  J -.-> L
~~~

**常见追问**

- **为什么不用一个大 Prompt？** Prompt 无法可靠承担权限、持久化、事务、幂等和恢复，需要确定性代码约束执行。
- **RAG 是 Agent 吗？** RAG 是检索增强能力；固定“检索后回答”可以是 Workflow，模型动态选择检索、查询和迭代才体现 Agent 控制流。
- **什么时候不用 Agent？** 路径稳定且风险高的任务优先用确定性流程；只把需要语义理解或动态决策的节点交给模型。
- **前端能贡献什么？** 展示任务进度、证据、工具状态和失败恢复，支持取消、重试、人工确认；执行权限与业务校验仍在服务端。

长任务可借鉴“初始化环境、分步执行、留下可续接产物”的设计；仅把历史压缩并不能保证跨会话任务完成。[Anthropic 长任务 Harness 设计](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

### 1.2 Claude Code 的三层记忆架构是什么？

**口述答案**

我会先确认“三层”指功能还是文件作用域。按功能，我会解释为当前工作上下文、显式持久规则和自动长期记忆。工作上下文承载本次任务，CLAUDE.md 等文件表达用户或团队规则，auto memory 保存跨会话的经验。这是便于理解的功能划分；官方文档明确区分的是显式指令文件与 auto memory 两类持久机制，并没有统一命名的“三层架构”。[官方记忆说明](https://code.claude.com/docs/en/memory)

**两种问法都要能接住**

| 划分 | 内容 |
| --- | --- |
| 按功能 | 工作上下文：本轮对话与工具结果；显式规则：人为维护的约定；自动记忆：从反馈中保留的经验 |
| 按指令作用域 | 用户级、项目级、局部目录或路径规则；此外还有组织托管策略与项目个人文件 |

常见文件包括用户级 `~/.claude/CLAUDE.md`、项目级 `CLAUDE.md`、项目个人 `CLAUDE.local.md`，以及子目录规则。auto memory 使用独立记忆目录及索引，按需读取详细内容；不要把所有文件都理解成启动时无条件全文加载。[文件作用域与加载规则](https://code.claude.com/docs/en/memory#choose-where-to-put-claudemd-files)

**追问：压缩之后会不会忘？**

会有风险。当前上下文是有限的，早期对话要求可能在压缩中损失；持续规则应写入持久指令，任务目标与进度还要保存在可重新读取的状态中。记忆是上下文来源，不能代替权限执行器或可靠事务。[Claude Code 工作原理](https://code.claude.com/docs/en/how-claude-code-works#the-context-window)

### 1.3 了解 DeepSeek Harness 吗，说说它整体的设计？

**口述答案**

DeepSeek Harness 是 DeepSeek 的开源 Agent 运行框架，核心思想是一切皆插件，底层由 Cordis 提供服务、事件和生命周期组合。模型适配、工具注册、会话日志、Agent Loop 都可以作为插件替换。它用配置组合不同运行形态，用事件把模型请求、工具执行和状态变化串起来，并从会话日志投影模型上下文。这种设计把能力扩展与具体执行循环解耦。

**按官方架构展开**

| 机制 | 作用 |
| --- | --- |
| Cordis 共享上下文 | 插件提供服务和事件扩展点，卸载时清理其注册效果 |
| Profile 与 Bundle | 按有序配置层组合插件树，组织 Web、headless、SDK 等运行方式 |
| 模型适配接口 | 隔离不同模型供应商的消息与流式响应差异 |
| Agent 与 Agent Loop | 定义运行接口，并由可替换驱动推进 turn 和 step |
| 工具流水线 | 工具注册、调用前处理、执行、调用后处理与结果记录 |
| Session Event Log | 追加记录持久事件，支持上下文投影、会话续接和观测 |

可以口述的主路径是：

~~~text
领取输入 → 组装提示词与可用工具
→ 模型请求与流式响应
→ 工具执行 → 记录结果
→ 判断继续或结束
~~~

**进一步的判断**

优势是扩展、替换和组合能力强；代价是插件依赖、事件顺序、生命周期与配置版本需要严格管理。插件化本身不等于安全隔离，也不保证外部工具副作用可以回滚。不要把“换插件”说成“任意情况下无缝恢复”。

以上对应 2026 年 11 月 9 日查阅的官方架构；具体包名与默认配置可能继续演进。[DeepSeek Harness README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)、[官方架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

### 1.4 一个完整的 Harness 至少包含哪些部分？

**口述答案**

Harness 是让模型能够在真实环境中持续完成任务的运行系统。我认为最少需要模型调用适配、执行循环、上下文与状态管理、工具注册执行、权限与资源边界、失败恢复，以及 Trace 和结果验证。模型决定“下一步做什么”，Harness 负责“是否允许、怎样执行、如何续接、何时停止，以及怎么证明做对了”。

**生产检查清单**

1. **模型适配**：统一输入输出、流式响应、用量统计、可重试错误分类。
2. **运行循环**：开始、等待工具、继续、完成、失败、取消；设置步数、时长和费用上限。
3. **上下文与状态**：目标、约束、已完成事项、证据、近期交互；持久化检查点。
4. **工具系统**：能力发现、Schema 校验、超时、并发控制、结构化结果。
5. **执行边界**：身份与权限、沙箱、敏感操作确认、幂等键。
6. **恢复机制**：区分可重试与不可重试错误，处理中断、外部副作用及恢复后的状态核对。
7. **观测与验收**：Trace、错误记录、业务完成检查、离线回归。

**追问：Checkpoint 能保证 exactly-once 吗？**

不能。检查点保存内部运行状态，外部写操作可能已成功但还没记录成功。恢复后必须依靠幂等键、操作流水、状态查询或补偿机制防止重复执行。多 Agent 和向量库都是可选能力，不是所有 Harness 的必需组件。

## 2 ReAct 模式

### 2.1 Agent 中 Plan-and-Execute 模式和 ReAct 模式有什么区别？

**口述答案**

ReAct 根据当前观察选择行动，再用结果修正下一步，适合探索性任务。[ReAct 原论文](https://arxiv.org/abs/2210.03629) Plan-and-Execute 先明确子任务和依赖，再执行并按需重规划，适合较长且目标可拆解的任务。区别主要是计划的显式程度、维护方式和执行粒度，不是“一个会思考、另一个不会”。实际可以外层维护计划、内层用 ReAct 执行一个子任务。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 控制方式 | 观察后决定下一步行动 | 先形成显式计划，再执行和更新 |
| 适合场景 | 调试、搜索、探索未知环境 | 调研报告、迁移、复杂业务任务 |
| 优点 | 反馈及时，适应环境变化 | 目标与依赖清楚，便于追踪完成度 |
| 风险 | 局部打转、重复调用、忘记全局目标 | 初始计划错误，计划过细或更新不及时 |
| 成本 | 可能多次全上下文模型调用 | 增加规划成本，但可精简子任务上下文 |

**设计示例**

“分析订单下滑原因”：外层计划拆成确认口径、查数据、拆维度、验证原因、形成结论；每个查询子任务内，根据数据库返回结果进行有限轮次的 ReAct。环境发生变化时更新计划，而不是强行执行过期步骤。

**追问：Plan-and-Execute 一定更省 Token 吗？**

不一定。规划、重规划和执行器之间传递信息都有成本。应在同一组任务上比较总调用量、任务成功率、时延和费用，不能只比较单次 Prompt。

### 2.2 怎么解决 ReAct 模式中死循环和路径重复的问题？

**口述答案**

我会做重复检测、进度判断和退出控制三层防护。同一状态下反复调用相同工具与参数，说明可能陷入循环；连续没有新证据或目标推进，需要重规划或换方法。运行时还要有最大步数、超时和费用预算，最终用验收条件判断完成。错误要分类，暂时性故障可以有限重试，参数错误或权限不足必须改变策略。

**具体实现**

- 对“工具名＋标准化参数＋相关状态版本”生成行动签名，识别同一状态下的重复；A→B→A 这类循环还要看短窗口的状态轨迹。
- 持久化已尝试方法、结果、失败原因和下一步；压缩历史时也要保留这些信息。
- 把进度定义成可检查条件，例如新增有效证据、通过一个验收项、修复一个测试；不能只用模型自报“有进展”。
- 工具结果结构化返回成功、错误类型、是否可重试和必要信息，避免只有一句“失败”。
- 无进展时依次选择补信息、换工具、缩小子任务、重规划；仍无法推进则明确阻塞或交给用户。
- 全局与单工具都有预算，重试也消耗预算；到达上限要结束并报告已完成与未完成部分。

**易错点**

重复调用并不总是错误：轮询后台任务、确认刚发生的状态变化可能必要。因此不能仅按工具名去重，要考虑状态、新证据、时间间隔和轮询目的。重试有副作用的调用前应确认幂等性。[AWS 有限重试与退避](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)

### 2.3 Agent 执行任务时路径反复、重复尝试，可能原因是什么？如何优化？

**口述答案**

我会先定位第一次重复开始的位置，检查当时目标是否清晰、工具是否给了有效观察、状态是否正确保存、模型是否看到了之前失败的原因。很多循环是信息或状态问题，单纯换模型或加一句“不要重复”治标不治本。修复后要用相同失败任务回放，比较重复率、有效步骤比例和最终成功率。

| Trace 里的现象 | 优先怀疑 | 对应优化 |
| --- | --- | --- |
| 相同参数一直报同一种错 | 参数契约不清、错误信息不足 | Schema 校验，返回字段级错误与可执行提示 |
| 已完成的子任务重新做 | 状态没写入、恢复或压缩遗漏 | 显式任务状态、检查点、重新注入完成事实 |
| 搜索词不停变化，结果相同 | 问题不明确、检索信号不足 | 拆子问题、维护证据缺口、必要时澄清 |
| 一直换方案，没有验收 | 目标或完成条件含糊 | 可验证里程碑，限制无进展重规划 |
| 写操作超时后再次写入 | 不知道外部操作是否成功 | 幂等键与业务状态查询，再决定是否重试 |
| 相似工具来回选择 | 工具描述重叠或目录过大 | 明确用途边界，按任务筛选工具 |

**验证口径**

同一状态的重复行动占比、每个成功任务的步骤数、无进展终止率、错误恢复率、最终成功率和 P95 完成时延。减少重复但同时降低成功率，不能算有效优化。

## 3 Context 工程

### 3.1 Agent 上下文越来越长，有什么应对方式？

**口述答案**

我会先控制进入上下文的信息量，再处理历史。日志和大文件先筛选，工具按需加载；当前目标、硬约束和任务状态保留为结构化信息，旧历史做摘要，原始证据保存在外部，需要时再取。任务之间相对独立时，可以分阶段执行或用独立上下文处理。触发压缩时要预留模型输出和工具返回的空间，不能等到窗口完全用满。

**按顺序实施**

1. **做预算**：为系统指令、任务状态、证据、近期消息和输出分别留空间；记录实际用量。
2. **减少源头噪声**：查询只取必要字段；大结果分页；日志按错误和时间筛选；完整产物存文件，返回摘要与位置。
3. **按需检索**：只取当前子任务需要的文件、记忆、工具和知识片段。
4. **维护任务状态**：目标、约束、已完成项与待办不能仅存在于一长串聊天中。
5. **滚动压缩**：保留近期完整交互，对较早历史做结构化摘要；维持工具调用与结果的协议配对。
6. **分解任务**：子任务使用限定上下文，返回结论、证据和未解决问题；分解有协调成本。

结构化笔记、历史压缩和按需获取信息是几种互补手段。[Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**追问：直接换更长上下文模型不行吗？**

可以作为容量手段，但噪声、成本、延迟和跨任务状态管理仍然存在。上下文长度够用，不代表模型稳定注意到全部重要信息。Prefix Cache 可以减少重复计算，也不会让这些 Token 从上下文窗口里消失。

### 3.2 上下文压缩时一般保留哪些关键信息？如何判断哪些内容可以被丢弃？

**口述答案**

判断依据是对后续决策是否必要，以及能否低成本、准确地重新获得。必须保留用户目标与硬约束、已确认事实、关键决策及原因、任务进度、失败路径、证据引用和下一步。重复日志、已过期的探索过程可以删除；大文件和原始工具结果通常移出当前上下文，保留可回溯的位置。

**一个可用的压缩状态结构**

~~~json
{
  "goal": "分析上月订单下降原因",
  "requirements": [
    {"id": "R1", "text": "仅统计已支付订单", "source": "用户确认"},
    {"id": "R2", "text": "使用北京时间自然月", "source": "用户确认"}
  ],
  "confirmed_facts": ["已确认订单表与支付时间字段"],
  "decisions": ["使用支付时间口径，排除创建时间口径"],
  "completed": ["确认指标定义"],
  "open_questions": ["退款是否从金额中扣除"],
  "failed_attempts": [
    {"action": "按创建时间统计", "reason": "不符合已确认口径"}
  ],
  "evidence_refs": ["metric-catalog:paid-orders:v3"],
  "next_step": "先澄清退款口径，再查询分渠道变化"
}
~~~

这是任务状态示例，字段应由应用校验，不是要求模型随意编写“已确认事实”。

| 内容 | 处理方式 |
| --- | --- |
| 用户明确要求、授权边界、验收条件 | 精确保留，尽量不改写关键数字、否定词和条件 |
| 已确认事实与关键决策 | 保留事实、依据、来源与适用范围 |
| 尚未完成的调用或事务 | 保留调用 ID、状态、恢复方式，避免断开调用与结果 |
| 失败方案 | 保留方法及失败原因，删除无用的长日志 |
| 大量原始数据与代码 | 保存外部产物、版本或摘要，按需读取 |
| 被用户撤销的旧要求 | 标为被取代，不继续作为有效约束 |
| 重复输出、寒暄、已无后续影响的中间尝试 | 可从活动上下文中移除 |

**易错点**

“丢弃上下文”不等于删除审计记录。摘要还应区分用户指令、外部资料和模型推测，防止把文档中的指令或未经证实的结论提升为任务约束。

### 3.3 如何避免 Context 压缩之后，模型忘记用户之前提出的重要要求？

**口述答案**

重要要求不能只依赖一段自然语言摘要。我会建立独立的需求清单，记录要求来源、优先级、状态和版本；用户纠正时显式更新。每轮构建上下文时重新注入有效要求，压缩前后检查清单是否完整，关键动作和最终结果再用程序验证可执行的约束。这样即使摘要有损，也有外部状态可以恢复。

**实现步骤**

1. 用户提出要求时提取候选约束；对影响结果的歧义进行澄清，不把推测当成已确认要求。
2. 给要求分配稳定 ID，保存原文或精确表达、来源、是否仍有效以及取代关系。
3. 将权限、金额上限、只读范围等可执行限制落实到代码或工具策略。
4. 压缩时明确输出尚有效的约束与未完成事项；检查旧清单中的有效 ID 是否仍被覆盖。
5. 恢复后从持久状态重新组装上下文，关键动作前检查相关要求。
6. 最终输出按验收清单检查，长任务评测覆盖“很早提出、很晚才生效”的要求。

**设计示例**

用户开头说“只分析，不修改数据库”，几十轮之后生成 SQL 时，仅靠模型记忆不足以保证安全。需求清单保留该要求，数据库工具使用只读权限，执行前再校验语句与允许的对象。

**追问：一直在每轮重复要求会不会浪费 Token？**

会，所以常驻的是简短、有效的硬约束；详细背景按需加载。稳定部分可利用前缀缓存，但更新过的要求必须立即生效，不能为了缓存而保留过期规则。

### 3.4 真实系统中，Context 压缩过后对 Prefix Cache 的影响有多大？Token 消耗量具体减少了多少？

**口述答案**

没有通用百分比，要把上下文长度、缓存命中和真实费用分开。压缩减少历史长度，但会改变历史前缀，原有缓存可能从变化位置开始无法复用；保持不变的前置规则仍可能命中，取决于供应商的缓存机制。还要加上生成摘要的成本，比较整个任务后续多轮的累计费用，不能只拿压缩前后的一次输入长度下结论。

**为什么缓存会受影响**

~~~text
压缩前：稳定规则 S | 旧历史 H         | 近期消息 R
压缩后：稳定规则 S | H 的新摘要 H'    | 近期消息 R
~~~

对于按精确前缀复用的缓存，H 改为 H' 后，H 之后即使有相同文字也不能简单“跨过不同前缀”复用。缓存边界、最小长度、有效期与请求配置都会影响实际命中。稳定规则、工具定义应保持内容和顺序稳定；动态摘要放在其后。[Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**输入长度演算示例**

假设稳定规则 8,000 Token，旧历史 40,000 Token，近期消息 8,000 Token；旧历史压成 6,000 Token：

~~~text
压缩前输入 = 8,000 + 40,000 + 8,000 = 56,000
压缩后输入 = 8,000 +  6,000 + 8,000 = 22,000
单次输入长度减少 = (56,000 - 22,000) / 56,000 ≈ 60.7%
~~~

**60.7% 只是这组假设的输入长度降幅，不是系统实测，也不是费用降幅。**

如果旧历史原本大量命中低价缓存，压缩后的新摘要需要重新计算或写入缓存，再加上摘要生成调用，第一轮费用甚至可能上涨。后续多轮都受益于短上下文时，才可能摊薄一次性成本。

**正确的核算方式**

~~~text
单次费用 =
  未缓存输入 Token × 对应单价
+ 缓存读取 Token × 对应单价
+ 缓存写入 Token × 对应单价
+ 输出 Token × 对应单价

总费用 = 所有任务调用与压缩调用的费用之和
费用降幅 = (未压缩方案总费用 - 压缩方案总费用) / 未压缩方案总费用
~~~

输入类别必须按供应商的计量规则统一，避免重复计算。例如 Claude 的 `input_tokens` 不包含单独统计的缓存读写部分，总输入要将三者相加；不能照搬到别家字段上。[缓存用量字段说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)

**实际会记录**

- 每次请求的总输入、输出、缓存读写 Token，压缩请求单独标记。
- 压缩后第一轮与后续轮次的缓存命中、首 Token 时延和总时延。
- 整个任务的累计费用、成功率、遗漏要求和因遗忘导致的重试。
- 同一评测集上的均值、中位数与长任务分桶，防止平均数掩盖退化。

被要求报自己的数字时，没有生产记录就回答测量方法；不要把上面的演算数字说成项目收益。

### 3.5 Context 压缩后的效果是如何检测的？

**口述答案**

我会从信息保留、任务行为和经济成本三个层面检测。在同一批长任务的相同检查点，对比保留完整历史和使用压缩历史的分支；看关键约束与事实是否保留、后续任务能否完成，以及累计时延与费用。压缩摘要写得通顺不代表有效，核心是模型继续执行时是否还会做对。

| 维度 | 测什么 | 示例 |
| --- | --- | --- |
| 信息保留 | 有效要求、关键事实、证据来源覆盖率 | 开头提出的只读要求是否还在 |
| 状态恢复 | 进度、待办、未完成调用是否正确 | 是否重复已完成步骤 |
| 行为结果 | 最终成功率、约束违反率、重复行动率 | 是否继续使用已否定口径 |
| 证据质量 | 引用是否可访问、摘要是否引入假事实 | 原文金额是否被改写 |
| 成本体验 | 全任务 Token、费用、P95 时延 | 是否因忘记而反复补查 |

**实验设计**

固定模型、工具、数据快照和任务条件；构造早期约束、多次用户纠正、长工具输出、多次压缩及中断恢复等场景。对非确定性任务重复运行，报告置信区间或至少波动范围；关键失败由人工审查。

信息保留可以定义为“被正确保留的有效关键项数 / 全部有效关键项数”。但所有约束并不等价，关键权限限制丢失不能被保留很多普通事实抵消。常规摘要相似度只能作辅助指标，不能作为业务验收。

### 3.6 如果 Skill 或 MCP 非常多，全部放进上下文中占用了太多部分，有什么办法解决？

**口述答案**

我会把能力发现与能力加载拆开。默认只提供简短目录或工具搜索入口，根据当前任务先筛选能力，再加载少量相关工具的完整 Schema 或 Skill 正文。工具执行产生的大结果也要筛选、分页或在代码里聚合后返回。这样同时控制定义和结果的上下文成本；再用工具选择正确率与任务成功率验证筛选有没有漏掉必要能力。

**分清两类内容**

- **Skill** 通常是操作方法、约定或工作流。可先读名称和用途，匹配后再读正文与必要资源。
- **MCP** 是连接工具与数据的协议。工具描述占不占上下文、如何延迟加载，由客户端和模型接口实现决定；MCP 本身不自动解决上下文膨胀。

**设计示例**

~~~text
任务 → 按权限过滤能力目录 → 检索相关能力
     → 加载所需说明与 Schema → 执行
     → 对结果筛选或聚合 → 返回必要证据
~~~

少量高频基础工具可以常驻；低频领域工具按需加载。相似能力要在描述里说明适用条件与差异，避免目录越精简、描述越模糊。发现失败时应允许扩大检索或询问，而不是假设工具不存在。

Claude 的 Tool Search 提供延迟发现与加载的具体实现；自建系统也可以实现“搜索工具目录 → 加载定义”的两阶段流程。[官方 Tool Search 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

**追问：只把工具 JSON 压缩一下不行吗？**

格式压缩能减少少量冗余，但无法解决几百个工具同时进入模型选择范围的问题。选择性加载通常更直接，同时仍要保留可执行 Schema、权限检查和必要的错误说明。

## 4 RAG 部分

先记住完整链路，后面的优化与排障都沿这条链路展开：

~~~text
离线：原始文档 → 解析清洗 → 结构化切块 → 元数据与权限 → 索引发布
在线：问题理解 → 稀疏/向量召回 → 融合去重 → 精排
     → 证据拼装 → 模型生成 → 引用与结果检查
~~~

### 4.1 BM25 召回的原理是什么？

**口述答案**

BM25 是基于词项匹配的相关性排序方法。一个词在文档中出现越多通常越相关，但收益会逐渐饱和；在语料中越少见的词区分度越高；还会做文档长度归一化，避免长文档天然占优势。工程上通过倒排索引找到含查询词的候选，再根据 BM25 得分取前几名，适合专有名词、编号和精确关键词，与向量召回互补。

**常见公式**

~~~text
BM25(q,d) =
Σ_{t∈q} IDF(t) × [ f(t,d) × (k1+1) ]
                    / [ f(t,d) + k1 × (1-b+b×|d|/avgdl) ]

一种常见的正值 IDF 写法：
IDF(t) = ln[1 + (N - n(t) + 0.5) / (n(t) + 0.5)]
~~~

| 符号 | 含义 |
| --- | --- |
| f(t,d) | 词 t 在文档 d 中出现的次数 |
| N、n(t) | 文档总数、包含词 t 的文档数 |
| 文档长度、avgdl | 当前文档的词项数、语料平均文档长度 |
| k1 | 控制词频饱和程度，值越大通常越晚饱和 |
| b | 控制长度归一化程度，b=0 表示不按长度归一化 |

这里是常见教学形式；具体引擎还可能有字段权重等处理。Lucene 文档给出了上面的 IDF 写法；Elasticsearch BM25 的默认参数为 k1=1.2、b=0.75，应在自己的语料上调优。[Lucene BM25Similarity](https://lucene.apache.org/core/9_9_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)、[Elastic Similarity](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

**追问：中文和行业黑话怎么办？**

分词、词典、同义词和字段设计很重要。BM25 本身不会自动理解两个业务别名的语义等价；错分专有词会影响检索。可增加别名字段，配合向量召回和领域词典。

### 4.2 准确率和召回率是什么？分别怎么检测？

**口述答案**

我会先确认这里的“准确率”是检索精确率 Precision，还是最终答案正确率。Precision 看返回结果里有多少相关项，Recall 看所有应找到的相关项里找到了多少。检索一般基于人工标注的相关集合测 Precision@K、Recall@K；答案正确率则需要单独评价生成答案，不能用检索分数替代。

~~~text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
Accuracy  = (TP + TN) / (TP + TN + FP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
~~~

TP 是找到的相关项，FP 是找到但不相关的项，FN 是遗漏的相关项，TN 是未返回且不相关的项。开放检索里 TN 很大，因此 Accuracy 往往不能反映搜索质量。

若返回 K 条结果，人工标注的相关集合是 R：

~~~text
Precision@K = |TopK ∩ R| / K
Recall@K    = |TopK ∩ R| / |R|
~~~

**演算**：Top 10 中 4 条相关，全部标注相关项有 8 条，则 Precision@10=40%，Recall@10=50%。返回不足 K 条时必须统一分母约定并记录实际返回量；没有相关证据的问题，单独评测正确拒答或澄清，不直接用零分母计算 Recall。

**检测流程**

1. 按真实问题分布抽样，建立问题、相关文档或证据片段的标注集。
2. 确定评价单位是文档、chunk 还是必需证据点；重复 chunk 不重复算成新的相关证据。
3. 固定索引快照、权限和模型版本，保存各阶段候选。
4. 在相同 K 下比较指标，按问题类型切片；人工复核争议与未标注候选。
5. 另外评估最终答案正确性、证据支持和引用准确性。

Hit@K 只看有没有至少一条相关结果；多证据问题即使命中一条，也不代表召回充分。MRR 关注第一个相关结果的名次，nDCG 能体现分级相关性和排序质量。大型语料很难穷尽标注全部相关项，应说明 Recall 是相对既有标注集的估计。

### 4.3 在 Text2SQL 场景中，针对行业黑话和专业术语，怎么解决召回不准的问题？

**口述答案**

我会把问题看成业务语义到数据库 Schema 的映射。先建立术语、别名和指标口径，再把这些定义关联到表、字段、连接关系和枚举值。检索时结合关键词、向量与结构化过滤，召回相关 Schema 和经过验证的问句 SQL 示例；生成前确认歧义，生成后做 SQL 校验与执行结果验证。只换 Embedding，通常无法解决业务口径本身不清楚的问题。

**分层处理**

| 层 | 需要补充的知识 | 示例 |
| --- | --- | --- |
| 词语与别名 | 缩写、行业词、产品别名 | 同一个业务系统的内部简称 |
| 指标语义 | 计算公式、状态、时间、币种、去重口径 | “支付金额”是否扣退款 |
| Schema Linking | 对应表、字段、主外键、聚合粒度 | 用户 ID 与订单 ID 的关系 |
| 值映射 | 自然语言实体到真实存储值 | “华东”对应哪个区域编码 |
| 查询范例 | 问句、正确 SQL、适用 Schema 版本 | 同类指标的标准查询 |

**设计案例**

假设企业把“动销商品”定义为“指定周期内至少有一笔满足条件的成交的商品”。系统不能只召回名称里有“商品”的表，还要找到成交状态、支付时间、商品标识与去重逻辑。若“成交”是否包括退款订单未定义，应先澄清或使用明确的企业指标定义，而不是凭模型猜测。

**工程重点**

- 给表和列补业务描述，保留主外键与连接路径，避免只召回孤立字段。
- 候选生成结合术语精确命中与语义召回，再对“问题＋Schema/定义”精排。
- 对枚举值和实体做受权限约束的查找，必要时展示少量脱敏样例。
- 维护词典和 Schema 版本，失效的 SQL 范例必须更新。
- SQL 执行使用只读权限、超时与资源限制，校验允许的表和操作。

**怎么验证**

分别看表/字段召回、指标映射、值匹配、SQL 执行成功和执行结果正确性；测试需覆盖多个数据状态，避免错误 SQL 恰好得到相同结果。SQL 能执行不等于业务口径正确。将 Schema Linking、任务分解和纠错分开处理，可参考 [DIN-SQL 论文](https://arxiv.org/abs/2304.11015)。

### 4.4 想要提升 RAG 的召回率，通常有哪些手段？

**口述答案**

先确认正确知识存在且能够被正确解析，再依次优化切块、查询表达、索引和召回策略。我会使用关键词与向量的混合召回，补充领域术语，必要时做多查询或问题分解，同时调整候选规模与 ANN 参数。最后用相同测试集看证据覆盖、最终质量和延迟，不能仅靠增加 Top K 判断优化成功。

**从上游到下游排查**

1. **数据覆盖**：文档有没有入库，OCR、表格和标题是否正确，版本是否过期。
2. **切块与元数据**：答案是否被切散；保留标题路径、相邻上下文、文档版本和适用范围。
3. **查询理解**：多轮指代补全、实体归一化、同义词与别名扩展，复杂问题拆子问题。
4. **多路召回**：BM25 处理精确词，向量处理语义；按情况补充结构化查询，再融合去重。
5. **向量与索引**：查询和文档使用匹配的模型与预处理，检查维度、距离函数和 ANN 搜索参数。
6. **候选预算**：适当扩大候选池，再精排到可供生成的规模；为多证据问题分配不同子问题的名额。
7. **训练优化**：已有代表性正负例时，再考虑领域适配或检索模型训练，并保留独立测试集。

**必须说清的取舍**

多查询、扩大 K 和相邻块扩展会引入噪声、成本与延迟。HyDE 等方法生成的是检索辅助文本，不能作为最终事实证据。Rerank 只能重排已召回候选，补不了候选之外的知识。

还应区分 **ANN Recall** 与 **业务 Recall**：前者比较近似搜索和精确向量近邻，后者比较返回结果和人工标注的相关证据；向量近邻找得准，不代表业务证据找得全。

### 4.5 RAG 离线阶段的 chunk 切分方式一般有哪些，分别有什么优势？

**口述答案**

常见有固定长度、递归边界、文档结构、语义切分，以及父子或层级切块。选择取决于文档结构和问题需要的证据粒度。我通常先按标题、段落、表格或代码结构切，再限制最大 Token；必要时做少量重叠或命中小块后扩展父块。最终通过召回、答案完整性、索引成本和延迟来决定参数。

| 方式 | 优势 | 主要问题与适用条件 |
| --- | --- | --- |
| 固定字符或 Token | 简单、成本低、易控制长度 | 容易切断句子、表格或代码；字符数不等于 Token 数 |
| 递归按段落与句子 | 在长度限制内优先保持自然边界 | 依赖标点和段落质量，扫描文档需先解析 |
| 按标题与文档结构 | 章节语义和来源清晰 | 要处理过长章节，并把标题路径传给子块 |
| 语义切分 | 按内容主题变化分段 | 额外计算成本，阈值与稳定性需要评测 |
| 父子或层级切块 | 小块提高匹配精度，父块补足上下文 | 父块过大会带入噪声；维护 ID 与层级关系 |
| 表格、代码等专用切分 | 保留列名、单位、函数或类的结构 | 解析和实现复杂；不能简单按换行切 |

固定、变长及按结构切分可以组合使用，重叠比例需随内容调整。[Microsoft 文档切块说明](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

**容易被追问的细节**

- overlap 是保留边界信息的策略，会增加重复和存储；不是越大越好。
- 表格子块要携带表头、单位和必要的行列语义，否则数字脱离上下文。
- 每块带上文档 ID、版本、章节、来源位置、权限与父块 ID，方便追溯和增量更新。
- 可先试几档 Token 长度和重叠比例，再根据测试集选择；不要把某个固定大小称为通用最优值。
- 分块变了，原来的 chunk 级标注也要维护，或尽量用原文证据区间作为稳定标注。

### 4.6 如果我的文档需要频繁更新，向量库应该怎么设计和选型？

**口述答案**

我会先设计更新链路，再选向量库。原始文档是事实来源，向量索引是可重建的派生数据。通过变更事件或 CDC 做增量解析、切块和向量化，用稳定文档 ID、版本、内容哈希和幂等写入管理更新；删除和权限变更也要同步。选型主要看数据规模、更新到可检索的延迟、过滤与一致性要求、混合检索能力和运维成本。

**一条可落地的更新链路**

~~~text
源文档变更 → 版本化事件 → 幂等消费
→ 解析与差异判断 → 只对变化内容重新 Embedding
→ 写入新版本索引 → 校验完整性与可检索性
→ 发布有效版本 → 清理旧块与失效缓存
~~~

建议保留：tenant_id、doc_id、doc_version、chunk_id、content_hash、embedding_model_version、权限、更新时间与删除标记。内容哈希用于复用向量计算；来源、权限等元数据改变时，即使正文未变也要更新。

**一致性和删除比 upsert 更容易出问题**

- 消费消息先检查版本，避免旧消息覆盖新版本；同一个事件重复投递应产生相同结果。
- 文档变短、重切块时，不能只 upsert 新块而遗留多余旧块。
- 多个 chunk 的写入通常不等于一笔跨系统事务。要求整篇一致可见时，可用“先暂存、再发布有效版本”的应用协议，并在查询时校验有效版本。
- 索引与源文档、多个检索系统之间要监控同步延迟和失败队列；最终一致的窗口必须可解释。
- Embedding 模型或切块规则整体升级时，在新索引完成构建与验证后再切换，并保留回滚能力。

Qdrant 同 ID 的重复 upsert 可以覆盖已有 point，集合别名支持原子切换；但这些能力不会自动解决源系统与索引之间的跨系统一致性。[Qdrant Points](https://qdrant.tech/documentation/manage-data/points/)、[Qdrant Collections](https://qdrant.tech/documentation/manage-data/collections/)

**选型时的条件判断**

| 已有条件 | 可以优先验证的方向 | 需要实测 |
| --- | --- | --- |
| 已有 PostgreSQL，向量需与业务数据关联 | PostgreSQL＋pgvector，利用事务和 JOIN | 查询规模、过滤后的召回、更新与索引维护开销 |
| 向量搜索是独立核心服务 | Qdrant 等专用向量数据库 | 混合读写、过滤、扩容、持久化与恢复 |
| 已有成熟全文检索，关键词与向量都重要 | Elasticsearch 等支持混合检索的系统 | 新鲜度、更新成本、精排延迟、运营复杂度 |

pgvector 提供 PostgreSQL 内的向量检索与增删改能力；Elastic 提供多路结果融合。表中是选型路径，不是性能排名。[pgvector 官方说明](https://github.com/pgvector/pgvector)、[Elastic 混合结果融合](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

验收时应模拟真实更新率与查询流量，测 P95 搜索延迟、更新到可检索时延、删除生效时间、业务召回与恢复时间，不能只测静态查询 QPS。

### 4.7 Rerank 的原理是什么，为什么能够优化 chunk 的排序？

**口述答案**

第一阶段召回追求大规模下的速度，向量检索通常把问题和文档分别编码，再按向量相似度选候选。常见的 Cross-Encoder 精排会把问题和一个候选片段联合输入模型，让两边的 Token 交互，判断这个片段是否真正满足问题，因此能更细致地处理条件、否定和实体关系。但计算成本更高，所以只对小候选集使用。[Sentence Transformers 检索与精排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

~~~text
Bi-Encoder：
query → 向量 q
chunk → 可预计算的向量 d
相似度(q, d) → 候选

Cross-Encoder：
[query, chunk] → 联合编码 → 相关性分数 → 重新排序
~~~

**设计示例**

可以先召回几十到上百条候选，去重后精排，取少量高质量证据交给生成模型。具体数量只是待评测参数；Reranker 的输入长度和推理成本会影响最优范围。

**常见追问**

- **为什么不全库精排？** 每个 query 和候选组合都要计算，面对大库成本过高，不能像独立文档向量那样全面预计算。
- **为什么精排后仍可能差？** 候选缺失、领域不匹配、重要内容被截断、标签偏差或多证据覆盖不足。
- **效果怎么测？** 固定候选集，看 nDCG@K、MRR、最终上下文的证据覆盖和答案正确率，再看新增时延。
- **分数一定是概率吗？** 不一定；取决于模型与输出变换，不能跨模型直接比较阈值。

Rerank 也可以用 LLM 进行逐项、两两或列表排序。这里解释的是常见 Cross-Encoder 方式；任何方式都不能凭排序找回候选集合中不存在的片段。

### 4.8 RRF 算法的公式是什么，K 一般设置多大？

**口述答案**

RRF 是按名次融合多个召回结果的方法。一个文档在各路中越靠前，或被多路共同召回，累计得分通常越高。公式是各路一除以“平滑常数加名次”后求和。平滑常数经常从 60 开始，但它不是召回数量 Top K；需要根据数据和各路候选窗口调优。[Elastic RRF 公式与默认值](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

~~~text
RRF(d) = Σ_{i: d∈L_i} 1 / (c + rank_i(d))

L_i：第 i 路返回列表
rank_i(d)：文档 d 在该路中的名次，从 1 开始
c：平滑常数；原题中的 K 通常指这里的 c
~~~

为避免与 Top K 混淆，这里用 c。某一路没有召回 d，该路贡献为 0；每路内部先按文档或证据 ID 去重。

**演算示例，c=60**

| 文档 | BM25 名次 | 向量名次 | RRF 得分 |
| --- | --- | --- | --- |
| A | 1 | 10 | 1/61＋1/70 ≈ 0.03068 |
| B | 2 | 2 | 1/62＋1/62 ≈ 0.03226 |

B 在两个列表中都靠前，融合后排在 A 前面。这只是公式演算，不是实际检索效果。

**为什么常用**

BM25 分数与向量相似度尺度不同，直接相加缺乏可比性；RRF 只用名次，减少了分数归一化的麻烦。代价是忽略了分数差距，也不会直接学习业务相关性。

**参数影响**

c 较小时头部名次优势更强；c 较大时各名次贡献差距变小，更强调多路一致性。还要区分每路候选窗口与最终返回条数，两者都会影响结果。加权 RRF 可以给不同路分配权重，但需在验证集上调参，保留独立测试集。

## 5 评测体系

### 5.1 一个完整严谨的评测流程应该怎么设计？

**口述答案**

先把业务成功定义清楚，再准备代表性数据和稳定环境，建立基线，按检索、生成、行动和最终状态分层评分。确定性条件优先用代码判断，开放式质量用有明确规则的模型评分，并用人工校准。每次改动对比同一批任务，多次运行观察稳定性，分析失败类型，达到质量、时延和成本门槛后再灰度上线，线上反馈继续进入回归集。

**从目标到发布的七步**

1. **定义成功与失败**：任务最终应达到什么状态，哪些约束不可违反，允许多长时间和多少成本。
2. **建立数据集**：覆盖常见任务、长尾、无答案、歧义、工具故障、多轮与高风险操作。
3. **固定环境和基线**：记录模型、Prompt、工具、索引及数据版本，隔离每次运行的可变状态。
4. **分层打分**：检索质量、答案与证据、工具参数、最终业务结果及副作用分别记录。
5. **处理随机性**：同一任务多次运行；使用配对比较，并报告样本量、分桶结果和波动。
6. **分析失败**：找到首次出错环节，按影响和频率排序；验证修复后是否引入其他回归。
7. **灰度与监控**：小流量验证真实体验，设置回滚条件，将新失败固化为后续回归。

**评分器怎么选**

| 评分器 | 适合 | 要防止 |
| --- | --- | --- |
| 程序规则与业务断言 | JSON 合法、SQL 结果、文件差异、权限、副作用 | 只检查格式而遗漏业务正确性 |
| LLM-as-a-Judge | 语义正确、证据支持、表达质量、开放式结果 | 偏爱长答案、顺序偏差、评分标准漂移 |
| 人工评审 | 业务歧义、重要失败、校准自动评分 | 标注不一致和样本选择偏差 |

模型评分要固定 rubric、评分器版本与输入信息；对两方案比较可隐藏方案名称、交换顺序，抽样与人工结果对齐。不能让同一个不稳定的模型分数成为唯一发布依据。

Agent 评测应检查真实环境中的最终状态；“模型说已经完成”不等于任务成功。Anthropic 对任务、单次尝试、评分器与最终结果的区分可作为参考。[Agent 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**追问：必须复现唯一正确的工具调用路径吗？**

不必。优先检查结果和必须遵守的行为约束，允许多条有效路径。只有业务要求明确规定的顺序、权限和步骤，才作为硬性轨迹规则。

### 5.2 一次评测中哪些东西需要记录？重点关注哪些指标？

**口述答案**

记录要足以解释差异并尽可能重放，指标要同时覆盖效果、效率和风险。我会保存任务与数据集版本、模型与参数、Prompt、工具和索引版本、实际输入输出、工具结果和最终状态；指标看任务成功、证据与答案质量、约束违反、时延、Token 和费用。只报一个“准确率”不能说明改动为什么有效。

**建议记录的内容**

| 类别 | 内容 |
| --- | --- |
| 样本 | case_id、任务类型、输入、约束、标准证据与验收条件 |
| 配置 | 代码提交、模型标识、采样参数、Prompt/Skill/工具版本 |
| 数据 | 文档或数据库快照、Embedding 与索引版本、权限条件 |
| 运行 | run_id、trace_id、各轮上下文引用、工具参数、结果、重试和终止原因 |
| 评分 | 各项得分、评分器版本、判分依据、人工复核与分歧 |
| 成本 | 分阶段时延、排队时间、输入输出与缓存 Token、费用 |

外部数据会变化，单纯保存问题与答案不能保证重放。应保存受控快照或可访问的产物引用；敏感内容按最小必要记录和访问控制处理。

**指标分层**

- **检索**：Recall@K、Precision@K、MRR/nDCG、无结果率、证据新鲜度。
- **生成**：答案正确性、证据支持率、引用是否对应结论、无依据断言与合理拒答。
- **Agent**：端到端任务成功率、工具参数正确率、重复行动、恢复成功与约束违反。
- **性能**：首 Token 时延、总完成时延、P50/P95、步骤数、排队时间。
- **成本**：单任务费用、总 Token、缓存用量、每成功任务成本。

~~~text
每成功任务成本 = 评测中所有任务的总费用 / 成功完成的任务数
~~~

这里要把失败尝试的费用也算进去；成功数为零时不能继续作普通除法。另需区分“单次尝试成功率”和“多试几次至少成功一次”，后者不能直接当成线上单次体验。

### 5.3 每次迭代都需要完整评测吗？想要更敏捷的评测流程，应该如何改造？

**口述答案**

不必每次都跑最贵的完整集，但每次都要有匹配变更风险的验证。我会做分层评测：本地跑快速冒烟和受影响模块测试，提交时跑关键回归与历史失败集，重要版本跑完整基准和长任务，最后用线上灰度验证。小集用于快速反馈，完整集防止只对熟悉案例优化。

| 阶段 | 主要内容 | 触发场景 |
| --- | --- | --- |
| 快速冒烟 | 基础任务、结构契约、关键权限与终止条件 | 每次相关修改 |
| 定向回归 | 受影响任务、关联能力与历史 badcase | Prompt、工具、检索策略变化 |
| 完整基准 | 代表性分布、长尾、多轮、成本与稳定性 | 重要发布或较广泛变更 |
| 生产验证 | 影子流量、灰度或受控 A/B | 离线达标之后 |

**提速方法**

- 建立“用例—能力—依赖”的映射，变更某个组件时找到需要覆盖的任务。
- 将模块级评测与端到端评测分开，避免每个小修改都运行完整长链路。
- 对内容和依赖均未改变的中间结果做缓存；缓存键包含数据与模型等版本。
- 固定快速集，同时轮换代表性样本，避免只优化一小组题。
- 沙箱中并行运行独立用例，遵守模型和工具限流，失败尽早反馈。
- 根据故障风险保留始终运行的强约束检查；模型、全局 Prompt、Embedding 等变化扩大覆盖。

**易错点**

改变了生成模型或检索策略，却直接复用旧答案或旧召回结果，会让评测失去意义。工具快照适合隔离变量，但发布前还要验证真实依赖，避免假环境掩盖超时、权限和状态变化。

### 5.4 离线评测效果 OK，但生产环境用户反馈体验不好，应该怎么处理？

**口述答案**

我会把“体验不好”转成可定位的问题，先抽取真实失败会话与 Trace，判断是答案不对、没有完成目标、等待太久，还是交互不清楚。再比较线上与离线的问题分布、数据新鲜度、权限、工具环境和评分标准。补齐缺失样本和指标后，做针对性修复，并通过受控线上验证确认用户体验确实改善。

| 差异来源 | 检查点 | 改进 |
| --- | --- | --- |
| 数据分布 | 离线多为短、清楚、单轮问题，线上有指代与歧义 | 增加真实多轮与长尾样本 |
| 数据新鲜度 | 离线快照有答案，线上索引未更新 | 新鲜度 SLO、更新与删除链路监控 |
| 依赖环境 | 离线工具稳定，线上限流、超时或权限不同 | 增加故障注入和真实依赖验证 |
| 指标错位 | 判分器喜欢完整长文，用户只需明确结论与操作 | 按用户任务重新定义成功与简洁度 |
| 产品体验 | 首字快但任务迟迟不结束、进度不明、无法取消 | 记录完成时延与退出，改善状态反馈 |
| 标注偏差 | 标准答案或自动 Judge 不符合业务口径 | 业务专家复核、重新校准评分器 |

**分析原则**

整体评分好可能掩盖某类用户持续失败，要按租户、任务类型、版本、时段和设备等切片。主动反馈的用户也不是随机样本，需要结合随机抽样、任务完成事件和失败会话审查。

线上 A/B 要预先定义主指标与保护指标；少量好评或一两次成功不能证明修复。对于会产生写操作的 Agent，影子执行应放在隔离环境，不能因为测试而重复产生真实副作用。

### 5.5 评测数据集应该怎么构造，重点关注哪些方面？

**口述答案**

我会以脱敏真实任务为主，结合业务专家补充和可验证的合成难例。数据要覆盖正常分布，也要单独覆盖低频高风险、无答案、歧义、多轮纠正和工具故障。每个样本包含任务条件、证据或最终状态要求、允许与禁止的行为。训练、开发和测试按文档、用户或时间隔离，避免近重复泄漏，并持续把线上失败加入回归。

**覆盖维度**

- 任务：简单问答、跨文档推理、Text2SQL、工具操作、长任务。
- 语言：简称、错别字、专业术语、多轮指代、模糊表达。
- 知识：新旧版本冲突、表格、无答案、不完整证据。
- 运行：工具超时、429、错误参数、部分成功、中断续接。
- 约束：租户隔离、权限、只读要求、取消、需要确认的操作。
- 难度：常见易例、难例、边界例，分别报告成绩。

**最小样本结构示例**

~~~json
{
  "case_id": "policy-017",
  "category": "rag_versioning",
  "query": "本月差旅住宿标准是多少？",
  "context": {"tenant": "tenant-a", "policy_version": "2026-11"},
  "required_evidence": ["travel-policy:2026-11:section-2"],
  "must_satisfy": ["使用当前有效政策", "说明适用地区", "给出来源"],
  "must_not": ["引用已失效版本", "读取其他租户政策"],
  "answerable": true
}
~~~

这只是测试样本设计，不包含实际差旅标准。行动任务则应补充初始环境、允许的操作及预期最终状态，不一定存在唯一的标准回答文本。

**质量控制**

标注标准要明确，重要或有争议样本由多位标注者复核。先按来源分组去重再划分数据集，避免同一文档的改写问题跨到开发集和测试集。合成题需人工或规则验证，防止问题、答案和证据共同出错。典型业务分布集与风险挑战集应分别报告，不用人为堆积难例后的平均分代替真实流量表现。

## 6 生产部分

### 6.1 现在线上的 RAG 系统准确率下降很多，你会怎样排查问题？

**口述答案**

先确认下降的是检索指标、答案正确率还是用户任务完成率，以及是否真的超出样本波动。然后划分时间、问题类型、租户和版本，严重时先回滚或降级。定位时沿入库、召回、精排、上下文和生成逐层检查，用相同失败请求比较新旧版本，找到第一个变差的环节，再通过单变量替换验证根因。

**排查顺序**

| 环节 | 问什么 | 看什么证据 |
| --- | --- | --- |
| 指标与流量 | 分母、评分器、流量分布是否变化 | 同口径样本、业务分桶、版本时间线 |
| 解析与入库 | 正确文档是否存在、完整且有效 | 文档版本、解析产物、更新队列、删除状态 |
| 召回 | 正确证据有没有进入候选 | 各路 Top K、查询改写、权限过滤、索引配置 |
| 精排 | 已召回证据是否被排到后面 | 精排前后名次、截断长度、模型版本 |
| 上下文 | 正确证据是否真的传给模型 | 实际请求内容、去重、预算、压缩记录 |
| 生成 | 模型是否使用正确证据与口径 | Prompt、模型、采样参数、引用和输出 |
| 运行依赖 | 有没有超时后悄悄走弱降级 | 工具错误、限流、备用路由和回退比例 |

**有说服力的定位实验**

- 在受控评测中把正确证据直接提供给生成阶段；若明显恢复，重点看检索与拼装。
- 固定生成模型和 Prompt，对比新旧索引；或固定索引，对比新旧生成配置。
- 对同一 query 检查 Embedding 模型、文档向量、维度、距离函数与预处理是否匹配。
- 查看权限过滤是否过严或错误；不能用取消权限过滤来“提高召回”。
- 对最终答案做人工复核，排除 Judge 或标准答案变更造成的假下降。

**修复后**

失败样本和同类边界样本进入回归集；灰度观察分桶成功率、P95 延迟、成本与新鲜度，验证是否真正恢复。回滚是止损手段，不能替代根因分析。

### 6.2 线上运行时的 Agent 系统，你会关注哪些指标？

**口述答案**

我会同时看任务是否做成、用户等多久、花多少钱以及执行是否可控。业务层看端到端完成率和用户重复操作，运行层看时延、错误、工具成功、循环与恢复，资源层看 Token、费用、并发、队列和限流。每项指标按任务类型、模型版本和租户分桶，告警围绕用户影响和 SLO，而不只盯 CPU。

| 类别 | 关键指标 | 主要用途 |
| --- | --- | --- |
| 业务质量 | 任务完成、人工接管、用户纠正、抽样正确性 | 判断真正解决了多少问题 |
| 延迟体验 | 首 Token、总完成、P50/P95/P99、排队时间 | 区分模型慢、排队慢、工具慢 |
| 稳定性 | 5xx、超时、429、工具失败、取消与恢复成功 | 定位供应商和执行链路异常 |
| 行为效率 | 每任务步骤、重复调用、无进展退出、预算耗尽 | 识别失控循环或过度探索 |
| 成本 | 单任务费用、每成功任务成本、缓存读写、模型分布 | 防止“答对了但不可持续” |
| 容量 | 在途调用、队列长度与最老任务等待、RPM/TPM | 判断是否接近服务能力上限 |
| 知识健康 | 索引新鲜度、空召回、旧版本命中、更新失败 | 防止知识过期或索引损坏 |
| 执行边界 | 未授权操作拦截、租户越界、异常写入 | 验证工具权限和业务约束 |

**追问：线上没有标准答案，怎么监控质量？**

结合可验证业务事件、随机抽样人工复核、校准过的自动评分和用户反馈。点赞、转化、追问和退款等只能是特定场景的信号，不能直接等同于答案正确。异常时保留足够 Trace 供定位，避免只有指标没有过程。

**告警设计**

“P95 变高”需要区分排队与执行；“请求成功率正常”也可能掩盖模型持续给出错误答案。高风险业务约束可以单独设置严格门槛，普通质量与性能则结合基线、样本量和影响范围判断。

### 6.3 Agent 系统一次运行的 Trace 会记录哪些东西？

**口述答案**

Trace 应把一个任务从接收、排队、模型决策、检索、工具执行到最终验收串起来。根节点标识任务，子 Span 标识各次调用，记录时间、版本、输入输出引用、状态变化和错误。这样既能看关键路径和费用，也能定位第一次错误。需要的是可检查的决策、行动与结果，不是依赖模型提供不可验证的内部思维过程。

**一棵示例 Trace**

~~~text
run
├─ queue_wait
├─ load_state_and_requirements
├─ retrieve
│  ├─ query_rewrite
│  ├─ keyword_search
│  ├─ vector_search
│  └─ rerank
├─ model_call_1
├─ tool_call
│  ├─ validate_and_authorize
│  └─ execute
├─ checkpoint_or_compaction
├─ model_call_2
└─ verify_and_finish
~~~

| 位置 | 记录内容 |
| --- | --- |
| 根任务 | trace/run/session ID、任务类型、租户标识、起止时间、最终状态 |
| 模型调用 | 模型与参数、Prompt 版本、输入输出引用、Token 与缓存、停止原因 |
| 检索 | 原始/改写问题、过滤条件、索引版本、候选 ID、分数、名次、最终证据 |
| 工具 | tool_call_id、工具版本、脱敏参数、权限判定、结果、超时与重试 |
| 状态 | 关键状态变化、检查点、压缩前后信息、继续或终止原因 |
| 验收 | 满足与未满足的条件、业务结果、评分与反馈关联 |

模型调用与工具调用可以作为 Agent 根 Span 的子节点，这是 OpenTelemetry GenAI 观测示例采用的组织方式。具体属性名应与使用的规范及 SDK 版本对齐。[OpenTelemetry GenAI 观测说明](https://opentelemetry.io/blog/2026/genai-observability/)

**工程细节**

- 用 parent_span_id 或明确的关联关系串起异步调用，别让工具日志脱离原任务。
- 并行步骤的耗时不能简单相加当作总延迟，要看关键路径；各调用费用则可按口径累加。
- 大输出保存为受控产物并记录 ID、版本与摘要；权限允许时才能重放原内容。
- Token、时延等基础元数据常规采集；敏感正文与工具参数按需脱敏和受控采样，不能把密钥写入 Trace。
- 错误或低质量任务可以提高留存比例，同时保留随机正常样本用于比较。

### 6.4 线上出现 badcase，你会怎么分析？举一个你遇到的例子。

**口述答案**

我会先明确预期结果与实际偏差，保留当时的 Trace 和配置，再在相同数据与权限下复现。沿流程找第一次偏离正确路径的位置，列出少量可验证假设，用对照实验确认根因。修复后同时验证原失败、相似边界和正常场景，最后灰度观察。讲案例时说明自己的职责和真实证据，避免只说“改了 Prompt，效果好了”。

**演练案例：知识更新后仍回答旧政策**

这是用于练习分析方法的假设案例，不能直接讲成自己的亲历。

1. **现象**：新政策已经发布，助手仍按旧标准回答，而且引用链接看上去正确。
2. **保留证据**：保存问题、Trace、用户权限、索引版本、检索候选及实际送给模型的文本。
3. **初步观察**：原始文档已更新，但候选中同时存在旧块和新块，精排将旧块放在前面。
4. **根因假设**：更新链路只写入新块，没有清理旧块；检索没有校验当前有效版本。
5. **验证**：检查同一 doc_id 的版本集合；在测试环境仅允许有效版本参与，复放同一问题，确认旧证据不再进入上下文。
6. **修复**：补上版本发布与过期块清理、删除传播、有效版本校验及答案缓存失效；确保乱序更新不会覆盖最新状态。
7. **回归**：覆盖文档变短、删除、乱序消息、重复消费、索引重建、权限变化与模型缓存结果。
8. **上线观察**：看旧版本命中率、更新生效时延、答案正确性、零结果率与查询延迟。

**为什么这个例子适合面试**

它说明“有引用”不代表“引用有效”，“模型回答错”也可能源于索引生命周期。真正有说服力的是检索与版本证据，以及修复前后的受控对比；没有实测结果就不要补造收益数字。

**用你的真实经历替换**

准备一个 90 秒案例：业务场景和你的职责约 15 秒，现象和证据约 20 秒，根因与修复约 35 秒，验证与剩余取舍约 20 秒。没有 Agent 生产经历，可以如实讲本地实验，或讲前端/后端故障定位经历，再说明哪些方法可迁移、哪些 Agent 风险还需要验证。

### 6.5 Agent 系统请求非常多，达到了模型并发上限，应该怎么解决？

**口述答案**

我会先区分在途并发、每分钟请求数和 Token 配额，找到真正瓶颈。短期在模型调用入口做全局限流、有界排队、优先级和超时取消，限制单个 Agent 的扇出；对暂时失败做有限退避。然后减少不必要模型轮次和 Token，使用结果缓存或经过验证的模型路由。持续供不应求时需要扩配额、增加可用模型容量或调整产品服务等级。

**先估算容量**

~~~text
λ_task：每秒到达的任务数
m：每任务平均模型调用次数，包含重试和子任务
W：每次模型调用平均占用时长，单位秒

模型调用到达率 λ_model ≈ λ_task × m
平均在途模型调用数 L ≈ λ_model × W
~~~

**演算示例**：每秒 2 个任务，每任务平均 4 次模型调用，每次占用 3 秒，则模型请求约 8 次/秒，平均在途约 24。若每次按限额口径消耗 3,000 Token，还需要约 480 RPM 和 144 万 TPM。这里只是稳态平均估算，还要给突发和尾延迟留余量。

若模型同时有并发上限 C、RPM 上限 R、TPM 上限 T，每调用平均计量 Token 为 t，可用以下关系粗估任务吞吐上界：

~~~text
任务/秒 ≲ min(C/W, R/60, T/(60×t)) / m
~~~

这是简化估算；若输入、输出或不同模型分别限流，要分别约束，实际准入还需考虑配额窗口与供应商规则。

**按层处理**

| 层 | 手段 | 注意事项 |
| --- | --- | --- |
| 接入 | 有界队列、租户配额、优先级、公平调度 | 无界排队只会把失败变成超长等待 |
| 调度 | 分布式并发控制、请求/Token 预算、内部扇出上限 | 多实例不能各自按完整供应商配额放行 |
| 执行 | 截止时间、取消传播、有限重试 | 重试也占资源，避免 SDK 与业务层重复重试 |
| 减负 | 缩短流程、按需上下文、限制无用输出、合并重复只读请求 | 对输出质量和任务完成做回归 |
| 缓存 | 稳定前缀缓存、带版本与权限边界的结果缓存 | 前缀缓存不等于免请求；限额计算依供应商规则 |
| 路由 | 简单任务用较轻模型，故障时用已验证备用路线 | 保持能力与业务正确性，避免降级后静默答错 |
| 容量 | 申请配额、购买足够容量；自部署再优化推理吞吐 | 扩 Web 服务实例不能突破供应商账户配额 |

对可重试错误，尊重服务端等待提示，采用有上限的指数退避和随机抖动，并保证副作用可安全重试；权限或参数错误通常应直接修正，不反复发送。[AWS 重试控制](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)

**验收指标**

队列等待、任务拒绝率、429/超时率、完成时延、成功率、租户公平性与每成功任务成本。只把并发拉高而让失败和尾延迟恶化，不算扩容成功。

## 面试追问练习

每题先在 60 秒内讲清核心，再用一个例子解释。回答卡住时回到对应题目。

| 追问 | 合格回答必须涉及 |
| --- | --- |
| 为什么不直接给模型所有工具和文档 | 信息相关性、选择成本、上下文预算、按需加载与测量 |
| 最大步数已经限制了，还为什么需要防循环 | 上限只兜底，需要识别无进展、状态缺失和工具契约问题 |
| 压缩了 60% 的输入，为什么钱没省 60% | 缓存读写价格、摘要调用、后续轮次、重复尝试和成功率 |
| Recall@50 很高，为什么答案仍然错 | 精排、最终 Top K、拼装截断、证据有效性、生成与指标口径 |
| 如何区分检索问题和生成问题 | 固定变量，观察阶段候选，受控注入正确证据作对照 |
| SQL 能执行，为什么还要评测 | 指标口径、连接基数、去重、时间边界、执行结果与权限 |
| LLM 评分和用户反馈相反，听谁的 | 明确业务目标、人工校准、样本偏差、受控线上验证 |
| 为什么扩了服务实例还在 429 | 共享模型配额、分布式限流、重试放大、Token 额度 |
| 中断恢复后如何防止重复扣款或重复写入 | 检查点与外部副作用区别、幂等键、业务状态核对与补偿 |
| 给一个实际优化数字 | 真实基线、固定样本、改动、前后结果、样本量与副作用 |
